# ゲームモデルの正規化提案

## 現状の問題点

現在の `Game` モデルでは、`Publisher`, `Platform`, `Series`, `Genre` が文字列として直接保存されています。これにより以下の問題が発生します：

1. **データの重複**: 同じ出版社名、プラットフォーム名が複数のゲームレコードに重複して保存される
2. **一貫性の問題**: 表記揺れ（例: "Nintendo" vs "任天堂"）が発生する可能性
3. **メンテナンス性の低下**: 出版社名の変更時に全レコードを更新する必要がある
4. **正規化の不備**: 第2正規形（2NF）の要件を満たしていない（部分関数従属が存在）

## 正規化の検討

### 正規化レベル

- **第1正規形（1NF）**: ✓ 満たしている（各フィールドが原子値）
- **第2正規形（2NF）**: ✗ 満たしていない（Publisher, Platform, Series, Genreが非キー属性として重複）
- **第3正規形（3NF）**: 2NFを満たせば自動的に満たす
- **BCNF**: 現時点では不要

### 正規化後の構造

以下のテーブル構造を提案します：

#### 1. Publisher テーブル
- **目的**: 出版社情報を管理
- **関係**: Game と 1対多（1つの出版社が複数のゲームを持つ）

#### 2. Platform テーブル
- **目的**: プラットフォーム情報を管理
- **関係**: Game と 多対多（1つのプラットフォームに複数のゲームが存在、1つのゲームに複数のプラットフォームが存在）

#### 3. Series テーブル
- **目的**: シリーズ情報を管理
- **関係**: Game と 1対多（1つのシリーズに複数のゲームが属する）
- **注意**: Game 側で NULL 許容（任意項目）

#### 4. Genre テーブル
- **目的**: ジャンル情報を管理
- **関係**: Game と 多対多（1つのジャンルに複数のゲームが属する、1つのゲームは複数のジャンルを持つ）
- **注意**: Game 側で NULL 許容（任意項目）

#### 5. Game テーブル（変更後）
- **変更点**: 
  - `Publisher` (string) → `PublisherID` (uint, 外部キー)
  - `Platform` (string) → `Platforms` (多対多リレーション、中間テーブル: `game_platforms`)
  - `Series` (*string) → `SeriesID` (*uint, 外部キー, NULL許容)
  - `Genre` (*string) → `Genres` (多対多リレーション、中間テーブル: `game_genres`)

#### 6. 中間テーブル
- **game_platforms**: Game と Platform の多対多関係を管理
- **game_genres**: Game と Genre の多対多関係を管理

## 正規化の妥当性検証

### 利点

1. **データの一貫性**: 出版社名、プラットフォーム名などの表記が統一される
2. **ストレージ効率**: 重複データが削減される
3. **メンテナンス性**: 出版社名の変更が1箇所で済む
4. **拡張性**: 各エンティティに追加情報（説明、URL等）を追加しやすい
5. **正規化の遵守**: 第2正規形（2NF）を満たす

### 考慮事項

1. **NULL許容**: Series は任意項目のため、外部キーを NULL 許容にする
2. **多対多関係**: Platform と Genre は多対多関係のため、中間テーブルを使用
3. **一意性制約**: Publisher, Platform, Series, Genre の Name に unique 制約を設定
4. **インデックス**: 外部キーにインデックスを設定してクエリ性能を向上
5. **Platform の必須性**: 現状のモデルでは Platform は必須項目のため、多対多関係でも少なくとも1つのPlatformが必要（バリデーションで実装）

### 潜在的な問題と対策

1. **API互換性**: 既存のAPIエンドポイントの変更が必要
   - リクエスト/レスポンス形式の変更
   - バリデーションロジックの変更

2. **クエリの複雑化**: JOINが必要になる
   - GORMの Preload を使用して関連データを取得
   - パフォーマンスへの影響を考慮

3. **多対多関係の管理**: Platform と Genre は配列として扱う必要がある
   - リクエストでは配列で受け取る
   - レスポンスでは配列で返す

## 実装時の注意点

1. **バリデーション**:
   - 外部キー（PublisherID, SeriesID）の存在確認
   - Platform と Genre の配列の各IDの存在確認
   - 必須項目のチェック（PublisherIDは必須、Platformsは少なくとも1つ必要）

2. **API設計**:
   - リクエストでは Platform と Genre を配列で受け取る
   - レスポンスでは関連エンティティの情報を含める（Preload）
   - Platform は必須項目のため、少なくとも1つのPlatformが必要（バリデーションでチェック）
   - Genre は任意項目のため、空配列も許容

3. **テスト**:
   - 既存のテストの更新
   - 新しいモデルのテスト追加
   - 多対多関係のテスト

## 結論

提案する正規化は、データベース設計のベストプラクティスに従っており、以下の点で優れています：

- ✅ 第2正規形（2NF）を満たす
- ✅ データの一貫性と整合性を向上
- ✅ メンテナンス性の向上
- ✅ 将来の拡張に対応可能

この正規化により、より保守性の高いデータベース構造を実現できます。
