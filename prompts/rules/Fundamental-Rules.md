# 開発規範 (General Coding Rules)

本規範は、コードの一貫性、品質、およびテスト容易性を確保するために、生成AI (LLM) および開発実務者が遵守すべき最低限の要件を定めます。

## 1. 計画策定における要件

実装作業のための計画をLLMに指示する際は、以下を遵守すること。

* **コードの記述禁止:** 計画文書内には、具体的な実装コードを記述してはならない。代わりに、**設計の詳細**を記述すること。

* **設計の要素:** 設計の詳細は、計画文書を読んだ者がコードの実装を明確にイメージできることを目的とし、最低限以下の要素を記述すること。

  * プロジェクトまたは機能の全体の構造説明。

  * 構造を分解した際の、各ファイルが持つ役割と機能の記述。

  * 各機能を実装する際の論理的な順序。

  * **テストの概要と計画:** どの機能を、どのような観点でテストすべきかを示す。基本的にテスト駆動（TDD）で実装を進めるよう計画すること。

## 2. ビルドとテスト方針

### 2.1 ビルドシステムと実行基準

* **統一された実行手段:** ビルド、テスト、および検証は、プロジェクトルートに存在する**所定のビルドスクリプト**（例: `build.sh` や `make all` 等）を実行することで実行すること。

* **バイナリ配置:** ビルドによって生成された実行可能ファイルや成果物は、所定の成果物フォルダ（例: `bin` または `dist`）以下に格納されること。

* **最終成功の定義:** コードの修正や追加にかかわらず、**最終的にビルドスクリプトがエラーなく正常に終了すること**をもって、ビルド成功と判断する。

* **局所的テストの許可:** エラー調査や開発効率を目的として、ビルドスクリプトを介さず個別のテストを局所的に実行することは許容する。ただし、これは中間確認の手段であり、最終的なビルド成功の判断基準とはならない。

### 2.2 コードの記述完了の定義（テスト駆動原則の適用）

新しい機能の実装または既存機能の修正は、以下のステップをクリアして**テスト駆動開発（TDD）の原則**に従って完了と定義される。

1. **結合テストの定義:** `tests/integration/` フォルダ以下に、要求仕様を満たすための**結合テスト**を先に記述すること。

   * 結合テストは、アプリケーションの振る舞いを外部から確認する仕様書として機能する。

   * 結合テストの適切な分類を維持するため、`tests/integration/` の構造に従うこと。

2. **ユニットテストの定義と実装:** 結合テストを仕様として、**ユニットテスト**を記述すること。その後、ユニットテストを通過させるために最小限の目的コードを記述すること。

3. **初期検証:** ユニットテストとビルドがエラーなく完了することを確認する（例: ビルドスクリプトを単体テストのみ実行するオプションで実行）。エラーが存在する場合は、コードまたはテスト設計を見直すこと。

4. **最終検証:** **結合テストがエラーなく完了することを確認する**（例: ビルドスクリプトを結合テストのみ実行するオプションで実行）。

結合テストまでエラーがないことを確認できた場合にのみ、コードの記述完了と見なす。

## 3. テスト原則と品質要件

### 3.1 テストの網羅性

* **全コードのテスト義務:** 原則として、**実装コードは全てペアとなるテストが記述されること**が義務付けられる。

* **テストの継続的修正:** 実装コードの修正や追加が行われた場合、それに合わせて**必ず対応するテストも修正または追加されること**。

### 3.2 テスト失敗時の対応

* テストが失敗した場合は、速やかに原因を究明し、修正に着手すること。

* **禁止事項:** 問題が解決できない場合であっても、**該当するテストを意図的にスキップしたり、エラー処理や実装コード自体をスキップして通過させたりすることは禁止**する。エラーとして報告されることが、異常な挙動に対する正しい振る舞いである。

### 3.3 単体テストと結合テストの区分

| **区分** | **目的** | **定義** | **外部通信/設定ファイル** | 
| **単体テスト (Unit Test)** | 該当コードのロジックが正常に動作するかどうかを判断する。 | 設定ファイル（コンフィグ）を読み込まなくても実行可能なテスト。ハードコードされたダミー値を利用できる。 | 外部通信を要する処理は、モックサーバー等を使用して**応答をダミー化**すること。 | 
| **結合テスト (Integration Test)** | アプリケーションの総合的な機能動作確認と、修正による他機能への影響を判断する。 | コンパイル済みのバイナリを利用し、**設定ファイルが無いと動作しない**テスト。 | **モックサーバーは使用しない**。外部APIとの連携は、実際に外部と通信して確認すること。 | 

## 4. ロギングと通信処理

### 4.1 ログの積極的利用

* **ログの義務化:** デバッグ及び運用監視の観点から、できる限り詳細なログを出力すること。

* **通信処理の記録:** ネットワーク通信が発生する処理においては、以下の情報を含んだログ出力を必須とする。

  * 通信開始前と完了後の正確な時刻。

  * 当該処理に要した時間。

### 4.2 Web APIエラーハンドリングとリトライ設計

外部通信を行うWeb API等の処理においては、以下の観点を考慮したリトライ設計が義務付けられる。

* **ログ:** エラー発生時やリトライ試行時には、必ずログを出力すること。ログには、可能であれば**リクエストの詳細とレスポンスの詳細**を含めること。

* **リトライ観点:**

  1. 接続時のエラー（例: ネットワーク接続の確立失敗）に対するリトライ。

  2. 接続できたが、処理時間が規定を超過した場合（タイムアウト）のリトライ。

  3. 接続後、結果を得たものの、結果内容がリトライによって解決が期待されるエラー（例: 一時的なサーバーエラー）であった場合の判定とリトライ。

# 技術スタック

このプロジェクトでは、以下の技術スタックを必ず使用すること。

- Windowsローカル環境で動作する
- 使用言語は Go（1.22 以上）とする
- Webフレームワークは Gin を使用する
- ORM は GORM を使用する
- データベースは SQLite を使用する

上記と異なる技術の提案・使用は禁止する。
要件と矛盾する場合は、その理由を説明し、本ルールを優先すること。
